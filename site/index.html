TL;DR
V8 speeds up your JavaScript by predicting what each line will do. While the prediction holds, that line stays on a fast path. A few ordinary-looking patterns break the prediction, and V8 moves to a slower path without saying so. Mark a TypeScript function with /** @jitmax */ and this checker reports those patterns in it, and in every function it calls whose source it can read.

The idea

V8 watches your code run. It notices what shape of data goes through each line, then compiles a version of that line which assumes the shape holds. The assumption is a bet, and it usually pays: that is most of why JavaScript is fast at all.

At the measured sites, V8 caches up to four object shapes. A fifth can move the site to a megamorphic lookup path. The JavaScript still returns the same result, so a functional test does not reveal that cost. jitmax looks for source patterns that can cause it; only a profile and benchmark can show whether it matters in your workload.

A handful of other patterns do the same kind of damage. Delete a key and V8 moves that object to a slower kind of storage and leaves it there. Rebuild an array from a copy of itself inside a loop and every pass copies everything the last pass built. None of it looks wrong on screen, which is why it survives review.

Use it

Run jitmax from the GitHub repository with bunx. Install Bun, then check bun --version. jitmax needs TypeScript >=5.0.0 <6, but no npm publication, release tag or build step. Bun runs the checker; its findings concern V8, not Bun's JavaScriptCore engine.

The public repository currently exposes no Git refs and its download returns 404. TC-133 tracks that access blocker. Every repository command below needs an accessible Git ref. GitHub documentation links share that access blocker. If you have a checkout, use the local route below and read its README.md.

Install your TypeScript project's dependencies with its usual package manager. Save this as hot.ts in that project's root: 

/** @jitmax */
export function total(rows: { value: number }[]): number {
  return rows.reduce((sum, row) => sum + row.value, 0);
}

Run from your project's root once the GitHub repository is accessible:

bunx github:kronael/jitmax --help
bunx github:kronael/jitmax hot.ts
bunx github:kronael/jitmax --verbose hot.ts

The sample exits 0 and reports every annotated function is clean. Mark your own hot function with /** @jitmax */ and pass its file next.

With an existing jitmax checkout, replace the quoted paths with your real paths; Windows paths can use C:/.... Install its dependencies once, then run from your project's root: 

cd "/path/to/jitmax"
bun install --ignore-scripts
cd "/path/to/your-project"
bun "/path/to/jitmax/bin/cli.js" hot.ts

For the commands below, replace bunx github:kronael/jitmax with bun "/path/to/jitmax/bin/cli.js" to use that checkout. The README holds the full setup and usage guide.

Paths choose files, not compiler options. The working directory determines which tsconfig.json jitmax reads. With no path argument it uses that config's file list; with neither paths nor a config it scans sources under the working directory.

Focus on megamorphic reads and calls

Save this as megamorphic.toml in your project's root. It disables the other six rules; coverage notices still apply. 

[rules]
megamorphic-elements = true
megamorphic-dispatch = true
accumulating-spread = false
chained-allocation = false
allocating-select = false
delete-property = false
closed-world = false
interface-dispatch = false

Run the checker with that config:

bunx github:kronael/jitmax megamorphic.toml hot.ts

To select different rules, edit the same table: false disables a rule and true leaves it enabled. Omitted rules stay enabled. The report states what you suppressed. An unknown rule name exits 2.

Select functions from a CPU profile

Record a V8 CPU profile with Node from your application's root. Replace your-workload.js with its JavaScript entry point and src with its source directory. This route needs no annotations. 

node --cpu-prof --cpu-prof-name=run.cpuprofile your-workload.js
bunx github:kronael/jitmax run.cpuprofile src

The default selects functions with at least 1% sampled self time. To change that threshold, add [profile] and min_self_pct = 2 on separate lines in your TOML file, then run bunx github:kronael/jitmax megamorphic.toml run.cpuprofile src. Transformed JavaScript needs source maps beside the generated files. The report names unmatched frames and exits 1 when coverage is incomplete. Pass at most one TOML file and one CPU profile.

Read a finding

Excerpt from bun bin/cli.js demo in the jitmax checkout:

demo/lib.ts:46  fiveShapes()
  error  megamorphic-elements
    demo/lib.ts:46:28
    related: demo/lib.ts:48:30 read: r.x
    next: inspect where these elements are built, not just this parameter.

Each finding names the source, a next: step and the sweep behind the rule. note: states behavior and measurement limits. related: links representative builders, implementations, allocations or key observers; sources: explains partial tracing. The default shows five related locations per finding. Add --verbose or -v to see all retained locations without changing the analysis. These locations do not prove runtime reachability or list every allocation.

A finding does not measure your workload. A benchmark ratio is a property of the input — the same rule measured 149–166x at n=1000 and 1766–1889x at n=10000 — and the annotation says the function is hot, not how large its data is. The numbers are on this page and in the bench/*.jl the finding names. Profile the caller, preserve its behavior, and benchmark the full operation before keeping a rewrite.

Every unsuppressed finding is an error and fails the run. Configure rules through a positional TOML file or a -rulename on the annotation. The report counts suppressed findings; coverage gaps still fail the run. Exit 0 means at least one function was checked with no remaining findings or reported coverage gaps. Exit 1 means findings, incomplete coverage or no selected functions. Exit 2 means the tool failed, including invalid input, configuration or source syntax. --help exits 0 without loading the project. A clean result does not prove that a rewrite is safe or faster.

What it looks for

Eight rules ship. The third column separates microbenchmarks from rewrites of real library functions. A faster isolated operation can still make its caller slower.

Each ratio is before time divided by after time. Above 1 means the rewrite took less time; below 1 means it took more time. A ratio of 1 means equal time. Build time, later reads and the full operation are different measurements. The ranges below apply only to the measured inputs, engine and hardware, not to your function.

The patternWhy V8 slows downMeasured, and what the number does not cover
a fifth shape of object reaching one line V8 remembers four. A fifth makes it look up every time. 3.4–11.3x on reads — highest in L1, lowest at RAM size, where memory bandwidth dominates instead. Two to four shapes cost 0.95–1.47x. The rule counts declared property sets, not runtime V8 maps. Objects with the same keys in different insertion orders can have different maps while this rule stays silent.
delete o.k the object moves to a slower kind of storage, and stays there 12.3–13.6x per property load. On es-toolkit's omit the own-property rebuild improves reads at both tested sizes, but the whole call is slower: 0.17–0.51x. Measure the caller's construction and reads together.
acc = [...acc, v] in a loop every pass copies everything the last pass built 149–166x at 1000 items. On radash's assign the whole call moves 1.18–3.54x. On remeda's mergeAll the own-property rewrite is slower at 8 inputs: 0.13x and faster at 64: 1.48–1.59x. Its read intervals span 1.0: no established read benefit. A clean result does not mean faster.
.map(f).filter(g) the first array is built, then thrown away 1.44–1.52x. A separate cell measured 6.48x, 6.58x and 7.51x across three sweeps. Their intervals share no value, so that cell is withdrawn. On zod's cleanEnum the same fix is worth 1.10–1.12x at a 16-member enum, and nothing this project will claim at 256: that cell measured 1.03–1.10x, which clears neither half of the protocol's broad-warning bar, so it is rejected and published as the rejection it is.
x = Lib.min(x, y) in a loop a fresh object every pass, even when nothing changed 2.60–2.89x. The recorded survey found allocations, but none matched the benchmark's unchanged-value case. Values advanced or were wrapped on every pass, so comparing first saved no allocation. Treat the rewrite as conditional advice, not a demonstrated win on those programs. BUGS.md TC-18.
a method called on five classes the call site sees five prototypes, and V8 stops caching the lookup 12.9–22.7x, the sharpest cliff this project measured. Four shapes cost 1.52–1.65x, so the step is at the fifth here too. It requires the CALL, not just the shapes, so it does not repeat the row at the top of this table.
a call into code it cannot read a callee too big to inline costs this much — and the checker cannot tell whether yours is 4.64–4.95x for a callee past V8's inlining budget. The rule makes no claim about your callee, and says so under every finding as known defect: TC-33. Node’s own API is not among its findings at all — calls into the platform are counted for the run and never listed. The checker cannot follow path.join. Nor is a method read off a value typed any: nothing resolves there, so the run reports what it could not see instead of naming a body it never found. Read it as coverage, not as cost.
a call through an interface the body is in the checkout; the walk just cannot tell which one runs A coverage finding, not a cost estimate. It has its own rule name, so you can suppress it without suppressing calls whose bodies are absent. The receiver’s origins are traced by dataflow, so a finding names the implementations that reach it instead of guessing from the type.

Findings in real TypeScript programs

The recorded survey runs the checker on library and application checkouts, with functions selected by examples/annotate.js. The examples survey holds the counts and run limits. In a checkout, read examples/README.md. These are detection examples, not measured speedups for those applications.

TypeScript 5.9.3: checker.ts:44260, checkUnusedIdentifiers, reads node.kind off every element of a PotentiallyUnusedIdentifier[], and that union is 20 distinct property sets at one load site. A union member is not a runtime V8 map. Profile the actual read before deciding whether to change the representation.

typescript-eslint 8.67.0: no-misused-promises.ts:543 calls tsNode.name.getText() on a name that reaches it as six distinct property sets. This is a method call, not just a property read. typescript-estree/src/ast-converter.ts:48 deletes range and loc from converted AST nodes when the parser is asked not to emit them. Any rewrite must preserve that absence, not merely assign undefined.

Those application checkouts had no dependencies installed. Their unresolved imports produce coverage findings, not evidence that the imports are slow. Install your project's dependencies before scanning. The recorded run counts describe those checkouts and checker revisions, not a fresh audit.

Why the numbers are worth anything

  • Every rule had to earn its place with a measurement. A constant in V8's source is a guess about cost until a benchmark prices it.
  • Every rule records where the same benchmark refused it, and a test fails if the rule fires there anyway. Four shapes is fine. Two shapes is fine. Only the fifth is reported.
  • Two rules also record a real cost they deliberately do not report. An object carrying its own function costs 3.5–15.8x from the second shape, and no declared type separates that from the case where four are free. The rule states that detection limit.
  • The element rule requires a property read off an element. Reading only rows.length does not trigger it. A cast such as (iss as any).path does not hide the underlying receiver type from that check. The chaining rule stays silent when a .slice(0, 10) in the chain bounds it three orders of magnitude below the smallest size its sweep covers, with the threshold read off the sweep rather than typed in.
  • A finding is counted once per source site, not once per caller. The report also names how many annotated functions reach it.
  • A finding carries no cost. It names the rule, the fix and the sweep. The ratio depends on the size of your data, the annotation does not carry that, and the checker does not time your function.
  • Every cell is measured three whole times. A cell whose three sweeps share no common value is withdrawn from published aggregates. Its raw observations remain available in bench/*.jl.
  • A sweep refuses to start when too many other threads are runnable. Each row records the machine state and allowed load. The corpus also contains measurements taken above a one-minute-load gate. Those rows remain in the evidence; that reading cannot establish whether another process competed with the benchmark. Read bench/README.md and docs/limits.md for the protocol and corpus limits.
  • Every number here is read out of the raw timing rows, never typed by hand. If a number and its data disagree, the test suite fails.

What it will not tell you

Whether your program is slow. It reports patterns that cost time when they are measured in a loop, on one machine, with one version of Node. If the line it flags runs twice, none of it matters. Profile first, then bring this to the function the profiler pointed at.

It will not follow a pattern across a function boundary either. The walk visits every callee whose source it can read, and each rule then matches inside one body — so a loop in one function and the copy that loop re-runs in another are invisible to both. The annotation widens where the rules are applied, not what any one of them can see.

Open defects are listed in BUGS.md, in the repository, at the same size as everything above.

jitmax

mark the function you need fast, and find out what is wrong with it

The middle of that is a real recording, not a mock-up — the checker running against a function radash ships, vendored into examples/ unchanged. make meme rebuilds the whole film from a clean checkout.

TL;DR
V8 speeds up your JavaScript by predicting what each line will do. While the prediction holds, that line stays on a fast path. A few ordinary-looking patterns break the prediction, and V8 moves to a slower path without saying so. Mark a TypeScript function with /** @jitmax */ and this checker reports those patterns in it, and in every function it calls whose source it can read.

The idea

V8 watches your code run. It notices what shape of data goes through each line, then compiles a version of that line which assumes the shape holds. The assumption is a bet, and it usually pays: that is most of why JavaScript is fast at all.

One line can keep four shapes in its head. Send a fifth through and the bet is off — V8 throws the specialised version away and goes back to looking the answer up, every call, forever. Your code still returns exactly what it returned before. There is no error, no warning, no log line. The function simply costs more than it did last week, and the profiler points at a line that looks completely ordinary.

A handful of other patterns do the same kind of damage. Delete a key and V8 moves that object to a slower kind of storage and leaves it there. Rebuild an array from a copy of itself inside a loop and every pass copies everything the last pass built. None of it looks wrong on screen, which is why it survives review.

Use it

Mark the function:

/** @jitmax */
export function total(rows: Row[]): number { … }

Point it at your source:

node /path/to/jitmax/bin/jitmax.ts src

It prints the line, what is wrong with it, the fix, and the sweep that priced the rule. It does not print a cost beside the finding: a ratio is a property of the input — the same rule measured 149–166x at n=1000 and 1766–1889x at n=10000 — and the annotation says the function is hot, not how large its data is. The numbers are on this page and in the bench/*.jl the finding names.

Each finding is an error or a warn, and only an error fails the run. A rule warns when no benchmark measures the program it fires on. It exits 0 when everything you marked is clean or only warned, 1 on an error or when it could not read your whole call tree, and 2 when the tool itself broke. A run that could not see everything is never a pass.

What it looks for

Eight rules ship. The third column carries the argument: the microbenchmark ratio first, then what the same fix did to somebody else's function. The second number is always smaller than the first, and three times it is below one.

On two programs nobody calls fast

Twelve utility libraries were surveyed the same way — cloned shallow, annotated by rule and not by hand. Between them the flagship rule fired on one function, and the sharpest cliff this project measured never fired at all. A library is a pipeline; neither shape lives there. So the same run went at two programs whose slowness is the reason other tools exist.

TypeScript 5.9.3, the compiler Microsoft is rewriting in Go for speed: 465 functions annotated, five megamorphic-element findings against ten in all twelve libraries. The widest is checker.ts:44260 — checkUnusedIdentifiers reads node.kind off every element of a PotentiallyUnusedIdentifier[], and that union is 20 distinct property sets at one load site, against the four V8 caches. A union member is not a V8 map, and that caveat holds here; 20 against 4 is still the widest gap this survey has found.

typescript-eslint 8.67.0, the linter every speed-first rewrite benchmarks itself against: 311 functions annotated, and megamorphic-dispatch fired for the first time on code this project did not write — no-misused-promises.ts:543 calls tsNode.name.getText() on a name that reaches it as six distinct property sets. Its plainest finding needs no caveat at all: typescript-estree/src/ast-converter.ts:48 deletes range and loc from every node of the converted AST, and every rule that reads those nodes afterwards reads them out of dictionary mode.

It also reported 4140 findings on that linter, and 4115 of them are one rule naming an import the program could not resolve, because the checkout had no dependencies installed. That is a defect in this tool, it is filed as BUGS.md TC-51, and it is why these two runs are quoted beside the twelve-library survey rather than folded into it.

Why the numbers are worth anything

  • Every rule had to earn its place with a measurement. A constant in V8's source is a guess about cost until a benchmark prices it.
  • Every rule records where the same benchmark refused it, and a test fails if the rule fires there anyway. Four shapes is fine. Two shapes is fine. Only the fifth is reported.
  • Two rules also record a real cost they deliberately do not report — a different thing, filed under the same heading until recently. An object carrying its own function costs 3.5–15.8x from the second shape, and no declared type separates that from the case where four are free. The rule misses it rather than guessing, and now says which of the two it is doing.
  • Two rules now read their own limit instead of printing it. The flagship rule used to report a megamorphic load from a parameter’s type without checking that anything read a property off it: on vue that was 46 findings, and 38 of them were functions touching nothing but rows.length. It now requires the read, and fires at eight distinct lines in 2,953 annotated functions across 22 codebases — five in the TypeScript compiler, two in vue, one in zod. The same survey caught that fix overshooting — reading the receiver’s type off (iss as any).path returned any, which silenced zod’s ten real findings along with the 38 — so the cast is unwrapped and they are back. The chaining rule stays silent when a .slice(0, 10) in the chain bounds it three orders of magnitude below the smallest size its sweep covers, with the threshold read off the sweep rather than typed in.
  • A finding is counted once per line, not once per caller. A line reached from 28 annotated functions used to be 28 findings, so the headline reported the call-graph fan-in rather than the work. The TypeScript compiler went from 90 errors to 24. The fan-in is still printed, on the finding, because a line reached by 28 callers is a better fix than one reached by one.
  • A finding carries no cost. It names the rule, the fix and the sweep. The ratio depends on the size of your data, the annotation does not carry that, and a number printed at a site that cannot support one is the defect this project spent a week finding in itself.
  • Every cell is measured three whole times. A cell whose three sweeps share no common value is withdrawn where the number is made, not noted in a log — 22 cells are withdrawn today, and two of them were headline numbers on this page a week ago.
  • A sweep refuses to start on a busy machine, and until 2026-08-21 that gate was reading the wrong number. It watched the one-minute load average, which on two cores was mostly the sweep’s own children, so it tripped on an idle machine and barely moved for a real tenant sitting behind it. It now counts runnable threads outside the harness, read as each row is written. The 592 rows published above the old gate are registered file by file in the test suite and withdrawn nowhere: the old reading cannot say which of them had a tenant, only that it was not answering the question. A new row over the reworked gate fails the build.
  • Every number here is read out of the raw timing rows, never typed by hand. If a number and its data disagree, the test suite fails.

What it will not tell you

Whether your program is slow. It reports patterns that cost time when they are measured in a loop, on one machine, with one version of Node. If the line it flags runs twice, none of it matters. Profile first, then bring this to the function the profiler pointed at.

It will not follow a pattern across a function boundary either. The walk visits every callee whose source it can read, and each rule then matches inside one body — so a loop in one function and the copy that loop re-runs in another are invisible to both. The annotation widens where the rules are applied, not what any one of them can see.

Open defects are listed in BUGS.md, in the repository, at the same size as everything above.

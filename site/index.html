jitmax

a command-line checker for TypeScript: mark the function you need fast, and find out what is wrong with it

The middle of that is a real recording, not a mock-up — the checker running against a function radash ships, vendored into examples/ unchanged. make meme rebuilds the whole film from a clean checkout.

TL;DR
V8 speeds up your JavaScript by predicting what each line will do. One line can keep four object shapes in its head; send a fifth through and the bet is off, and V8 moves that line to a slower lookup without saying so. Your code still returns what it returned before, so a functional test reveals nothing. Mark a TypeScript function with /** @jitmax */ and this checker reports those patterns in it, and in every function it calls whose source it can read. Only a profile and a benchmark of your own caller can say whether they cost anything. The README explains the mechanism in full.

Use it

Run jitmax from the GitHub repository with bunx. Install Bun, then check bun --version. jitmax needs TypeScript >=5.0.0 <6, but no npm publication, release tag or build step. Bun runs the checker; its findings concern V8, not Bun's JavaScriptCore engine.

jitmax needs TypeScript 5.x. It parses with the compiler your project builds with and needs the 5.x compiler API. If your project does not already depend on TypeScript 5.x, run bun add --dev typescript@^5.9, or npm install --save-dev typescript@^5.9; bun add typescript installs 7.x today, whose API has no sys host. If the compiler jitmax resolves has no sys host, the scan stops at exit 2 and asks you to install a supported TypeScript 5.x version.

Install your TypeScript project's other dependencies with its usual package manager too. Save this as hot.ts in that project's root: 

/** @jitmax */
export function total(rows: { value: number }[]): number {
  return rows.reduce((sum, row) => sum + row.value, 0);
}

Run from your project's root:

bunx github:kronael/jitmax --help
bunx github:kronael/jitmax hot.ts
bunx github:kronael/jitmax --verbose hot.ts

The sample exits 0 and reports every annotated function is clean. Mark your own hot function with /** @jitmax */ and pass its source directory next. A single file brings in the files it imports but not the files that import it, so a caller in the next file reads as no visible caller.

With an existing jitmax checkout, replace the quoted paths with your real paths; Windows paths can use C:/.... Install its dependencies once, then run from your project's root: 

cd "/path/to/jitmax"
bun install --ignore-scripts
cd "/path/to/your-project"
bun "/path/to/jitmax/bin/cli.js" hot.ts

For the commands below, replace bunx github:kronael/jitmax with bun "/path/to/jitmax/bin/cli.js" to use that checkout. The README holds the full setup and usage guide.

Paths choose files, not compiler options. The working directory determines which tsconfig.json jitmax reads. With no path argument it uses that config's file list; with neither paths nor a config it scans sources under the working directory.

Focus on megamorphic reads and calls

Save this as jitmax.toml in your project's root. It disables the other six rules; coverage notices still apply. 

[rules]
megamorphic-elements = true
megamorphic-dispatch = true
accumulating-spread = false
chained-allocation = false
allocating-select = false
delete-property = false
closed-world = false
interface-dispatch = false

Run the checker with that config:

bunx github:kronael/jitmax jitmax.toml hot.ts

To select different rules, edit the same table: false disables a rule and true leaves it enabled. Omitted rules stay enabled. The report states what you suppressed. An unknown rule name exits 2.

Select functions from a CPU profile

Record a V8 CPU profile with Node from your application's root. Replace your-workload.js with its JavaScript entry point and src with its source directory. This route needs no annotations. 

node --cpu-prof --cpu-prof-name=run.cpuprofile your-workload.js
bunx github:kronael/jitmax run.cpuprofile src

The default selects functions with at least 1% of your project's sampled self time; time in dependencies, Node's internals and the engine is left out. To change that threshold, add [profile] and min_self_pct = 2 on separate lines in your TOML file, then run bunx github:kronael/jitmax jitmax.toml run.cpuprofile src. If a build step writes the JavaScript from TypeScript, have it emit source maps — sourceMap: true for tsc. The report names unmatched frames and exits 1 when coverage is incomplete. Pass at most one TOML file and one CPU profile.

Read a finding

A real finding, from a five-member union saved as shapes.ts and scanned with bunx github:kronael/jitmax shapes.ts: 

  shapes.ts:9  total()
    shapes.ts:9:23  error  megamorphic-elements
      rows has 5 distinct property sets in its element type; this is a
      candidate for megamorphic load feedback, not an observed runtime map
      count
      related: shapes.ts:11:34 read: row.x
      sources: No builder located for this value. Source tracing is partial:
               no visible caller of total — its arguments come from outside
               this program.
      next: inspect where these elements are built, not just this parameter.
            If semantics allow, use consistent own properties and insertion
            order; benchmark the full caller including construction
      note: type assertions do not change runtime shapes. Adding a missing
            property can change key enumeration and presence checks. Library
            callers may need an upstream change; no automatic rewrite is
            established here
      measured in bench/shape-sets.jl and bench/shapes-calibrated.jl
      known defects: TC-2, TC-9

Each finding names the source and a next: step, and the sweep behind its rule when the rule has one; interface-dispatch has none. note: states behavior and measurement limits. related: links representative builders, implementations, allocations or key observers; sources: explains partial tracing. The default shows five related locations per finding. Add --verbose or -v to see all retained locations without changing the analysis. These locations do not prove runtime reachability or list every allocation.

A finding does not measure your workload. A benchmark ratio is a property of the input — accumulating-spread, a different rule, measured 149–166x at n=1000 and 1766–1889x at n=10000 — and the annotation says the function is hot, not how large its data is. The numbers are on this page and in the bench/*.jl the finding names. Profile the caller, preserve its behavior, and benchmark the full operation before keeping a rewrite.

Every unsuppressed finding on a per-call path is an error and fails the run. A finding reached only through a static field initializer prints warn with a once: line naming the initializer, because that code runs when its class is defined and not on each call, and does not fail the run. Configure rules through a positional TOML file or a -rulename on the annotation. The report counts suppressed findings. Coverage gaps still fail the run; the two coverage rules can be switched off, and the calls they report then stay unchecked at exit 0. Exit 0 means at least one function was checked with no errors and no reported coverage gaps. Exit 1 means an error, incomplete coverage or no selected functions. Exit 2 means the tool failed, including invalid input, configuration or source syntax. --help exits 0 without loading the project. A clean result does not prove that a rewrite is safe or faster.

What it looks for

Eight rules ship. The third column separates microbenchmarks from rewrites of real library functions. A faster isolated operation can still make its caller slower.

Each ratio is before time divided by after time. Above 1 means the rewrite took less time; below 1 means it took more time. A ratio of 1 means equal time. Build time, later reads and the full operation are different measurements. The ranges below apply only to the measured inputs, engine and hardware, not to your function.

The patternWhy V8 slows downMeasured, and what the number does not cover
a fifth shape of object reaching one line V8 remembers four. A fifth makes it look up every time. 3.4–11.3x on reads — highest in L1, lowest at RAM size, where memory bandwidth dominates instead. Two to four shapes cost 0.95–1.47x. The rule counts the property sets it can see, not runtime V8 maps. Objects with the same keys in different insertion orders can have different maps while this rule stays silent.
delete o.k if o has k, it moves to a slower kind of storage, and stays there 12.3–13.6x per property load. On es-toolkit's omit the own-property rebuild improves reads at both tested sizes, but the whole call is slower: 0.17–0.51x. Measure the caller's construction and reads together.
acc = [...acc, v] in a loop every pass copies everything the last pass built 149–166x at 1000 items. On radash's assign the whole call moves 1.18–3.54x. On remeda's mergeAll the own-property rewrite is slower at 8 inputs: 0.13x and faster at 64: 1.48–1.59x. Its read intervals span 1.0: no established read benefit. A clean result does not mean faster.
.map(f).filter(g) the first array is built, then thrown away 1.44–1.52x. A separate cell measured 6.48x, 6.58x and 7.51x across three sweeps. Their intervals share no value, so that cell is withdrawn. On zod's cleanEnum the same fix is worth 1.10–1.12x at a 16-member enum, and nothing this project will claim at 256: that cell measured 1.03–1.10x, which clears neither half of the protocol's broad-warning bar, so it is rejected and published as the rejection it is.
x = Lib.min(x, y) in a loop a fresh object every pass, even when nothing changed 2.60–2.89x. The recorded survey of 2953 annotated functions found no site. Treat the rewrite as conditional advice, not a demonstrated win. BUGS.md TC-18.
a method called on five classes the call site sees five prototypes, and V8 stops caching the lookup 12.9–22.7x, the sharpest cliff this project measured. Four shapes cost 1.52–1.65x, so the step is at the fifth here too. It requires the CALL, not just the shapes, so it does not repeat the row at the top of this table.
a call into code it cannot read a callee too big to inline costs this much — and the checker cannot tell whether yours is 4.64–4.95x for a callee past V8's inlining budget. The rule makes no claim about your callee, and says so under every finding as known defect: TC-33. Node’s own API is not among its findings at all — calls into the platform are counted for the run and never listed. The checker cannot follow path.join. Nor is a method read off a value typed any: nothing resolves there, so the run reports what it could not see instead of naming a body it never found. Read it as coverage, not as cost.
a call through an interface no single implementation to check: several may be here, or the receiver comes from outside the program A coverage finding, not a cost estimate. It has its own rule name, so you can suppress it without suppressing calls whose bodies are absent. The receiver’s origins are traced by dataflow, so a finding names the implementations that reach it instead of guessing from the type.

Findings in real TypeScript programs

The recorded survey runs the checker on library and application checkouts, with functions selected by examples/annotate.js. The examples survey holds the counts and run limits. In a checkout, read examples/README.md. These are detection examples, not measured speedups for those applications.

TypeScript 5.9.3: checker.ts:44260, checkUnusedIdentifiers, reads node.kind off every element of a PotentiallyUnusedIdentifier[], and that union is 20 distinct property sets at one load site. A union member is not a runtime V8 map. Profile the actual read before deciding whether to change the representation.

typescript-eslint 8.67.0: no-misused-promises.ts:543 calls tsNode.name.getText() on a name that reaches it as six distinct property sets. This is a method call, not just a property read. typescript-estree/src/ast-converter.ts:48 deletes range and loc from converted AST nodes when the parser is asked not to emit them. Any rewrite must preserve that absence, not merely assign undefined.

Those application checkouts had no dependencies installed. Their unresolved imports produce coverage findings, not evidence that the imports are slow. Install your project's dependencies before scanning. The recorded run counts describe those checkouts and checker revisions, not a fresh audit.

Why the numbers are worth anything

  • Every rule that reports a slowdown had to earn its place with a measurement. A constant in V8's source is a guess about cost until a benchmark prices it.
  • Every rule that reports a measured slowdown records where its benchmark refused it, and a test fails if the rule fires there anyway. Two to four shapes are not reported; only the fifth is.
  • Two rules also record a real cost they deliberately do not report. An object carrying its own function costs 3.5–15.8x from the second shape, and no declared type separates that from the case where four are free. The rule states that detection limit.
  • The element rule requires a property read off an element. Reading only rows.length does not trigger it. A cast such as (iss as any).path does not hide the underlying receiver type from that check. The chaining rule stays silent when a .slice(0, 10) in the chain bounds it two orders of magnitude below the smallest size its sweep covers, with the threshold read off the sweep rather than typed in.
  • A finding is counted once per source site, not once per caller. The report also names how many annotated functions reach it.
  • A finding carries no cost. It names the rule, a next step and, when the rule has one, the sweep. The ratio depends on the size of your data, the annotation does not carry that, and the checker does not time your function.
  • Every cell is measured three whole times. A cell whose three sweeps share no common value is withdrawn from published aggregates. Its raw observations remain available in bench/*.jl.
  • A sweep refuses to start when too many other threads are runnable. Each row records the machine state and allowed load. The corpus also contains measurements taken above a one-minute-load gate. Those rows remain in the evidence; that reading cannot establish whether another process competed with the benchmark. Read the benchmark protocol and the known limits before applying a suggested change.
  • Every number here is read out of the raw timing rows, never typed by hand. If a number and its data disagree, the test suite fails.

What it will not tell you

Whether your program is slow. It reports patterns that cost time when they are measured in a loop, on one machine, with one version of Node. If the line it flags runs twice, none of it matters. Profile first, then bring this to the function the profiler pointed at.

It does not always follow a pattern across a function boundary. The walk visits every callee whose source it can read, but the repeated-copy rule matches inside one body — so a loop in one function and the copy that loop re-runs in another go unreported. Other rules do trace values across calls.

Open defects are listed in BUGS.md, in the repository, at the same size as everything above.

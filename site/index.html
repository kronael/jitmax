turbocharge

mark the function you need fast, and find out what is wrong with it

TL;DR
Mark a function with /** @turbocharge */. turbocharge checks that function and every function it calls against seven rules, and gives you the file, the line, the measured cost and the fix. Every rule carries a rerunnable benchmark, the measured case where it must stay silent, and its mechanism traced to V8's own source — verified line by line by make v8-check. An eighth rule was withdrawn this week when its own benchmark refused it.

What it checks

The walk covers the annotated function and every callee TypeScript resolves to real source. A package that ships a .d.ts binds the call to the declaration, so most typed dependencies are the edge rather than the interior. Every call that cannot be followed is listed by name, and a walk that hits its 200-body cap prints WALK TRUNCATED and is not reported as clean. 

/** @turbocharge */
export function total(rows: Row[]): number { … }

What the fix is worth on somebody else's code

Every ratio above is a microbenchmark. This is the other question: does doing what the tool says make a real function faster? Three functions vendored verbatim from shipped MIT libraries, each paired with the fix turbocharge printed and nothing else. The function was chosen by a program, examples/annotate.js, not by taste, and the checksum must match between the two halves or the cell throws.

FunctionFindingWhole call, three sweeps
radash assign accumulating-spread 3.15-3.30x at 16 keys, 4.32-4.88x at 128
es-toolkit omit delete-property 1.64-1.79x at 12 keys, 3.24-3.36x at 48
remeda mergeAll accumulating-spread 1.31-1.36x at n=8; at n=64 the three sweeps disagree, so there is no number

The gap is the point. The rules behind these findings cite 12x and 188-203x. The whole call moves 1.3-4.9x, because a real function also allocates, branches and formats. That is what you actually get, and it is published here rather than left for you to discover.

Two cells went against the tool, and they are here at the same size. The fix accumulating-spread prints makes mergeAll's reads 8x slower — six of six sweeps — because Object.assign in a loop leaves the object in dictionary mode where the spread left it fast. And omit's read advantage rejects at 48 keys, because building 46 keys one at a time normalizes the fixed object too. A rule's printed fix can cost more than the defect it names. Tracked as BUGS TC-16.

Why the numbers are worth trusting

Every ratio on this page comes from the same protocol, and the raw per-pair timings ship next to every aggregate so you can recompute the intervals yourself.

Rule of the protocolWhy
One fresh OS process per observation An in-process A/B shares inline caches. Contamination is one-way, so the second variant measured is never independent.
AB/BA order randomised across 20 paired runs Order is a confound large enough to invert a result.
Checksums compared inside every pair A variant that computes something different is a failed run, not a fast one.
95 % bootstrap interval; a cell whose interval spans 1.0 is rejected A point estimate without an interval cannot separate a small effect from no effect.
Each side calibrated to a 120 ms timed region, sized from warm cost Sizing from a cold probe starves the slower variant of repetitions and inflates its ratio.
A cell that misses that region by more than 2x throws A mis-sized cell is a different measurement, not a noisy one, and must never reach publication.
Every published cell is run three times over, and the three answers are printed together A bootstrap interval resamples the pairs of one sweep, so it cannot see anything that varies between two. Near-identical work measured 1.64x, 0.91x and 0.89x — no two of which can both be true. Agreement now means a value common to all three intervals, which the intervals supply rather than something this project picks. Where they disagree the cell is dropped and the three numbers are printed anyway. Re-measuring 33 cells this way cost the project its most-quoted number: 2348x fell outside its own replications and is now 1750-2011x. BUGS TC-11.

The rules are held to the same standard as the code. Each records the condition under which its own benchmark found no effect, and a test asserts it stays quiet there. A rule that fires in a case its measurement rejected fails the build. Where a rule has an obvious objection, the objection is measured: the allocation allocating-select reports still costs 1.72-2.28x when it never leaves the function, so escape analysis does not remove it.

The second evidence

Every rule also carries its mechanism traced to V8's own source, in docs/v8-evidence.md, pinned to V8 15.3.0.0 and verified line by line — make v8-check re-reads 292 quoted lines across 23 files and fails if any has drifted. DEFAULT_MAX_POLYMORPHIC_MAP_COUNT 4 at src/flags/flag-definitions.h:3321, enforced at src/ic/ic.cc:798, is the same fact as the measured cliff at the fifth shape, reached from the opposite direction.

A source citation is a mechanism, never a magnitude, and the document says so for every rule. It is silent on all eight magnitudes. It gives accumulating-spread no citation at all, correctly: quadratic work is quadratic on any engine. And it contradicts one shipped threshold — a call site holds one target as a weak reference and has no polymorphic tier (src/builtins/ic-callable.tq:107), so a method kept in a field, rather than on a prototype, is off the cliff at two rather than five. That is BUGS TC-13, found by the benchmark and then predicted from the engine.

The fifth shape is a step, not a slope. Below it the cost is real and small, 1.2x to 2.0x, and it does not rise monotonically. Four maps fit the inline cache and cost a few extra map checks; the fifth does not fit, and the load becomes a hash lookup. That gap is why the rule starts at five.

With object construction counted in the same loop the five-shape cost falls to 1.25-3.52x, because allocation dominates the load. Both halves are measured for every rule.

What it refuses to warn about

A measured "no" ships here the same way a rule does. Three things this tool could plausibly warn about, and does not, because the benchmark said not to.

PatternMeasuredWhy no rule
a mixed element type, (number | string)[] 0.96-1.08x this one withdrew a shipped rule. Boxing is real — 1.39-1.66x on reads — but V8 picks the representation from the values actually stored, not the declared type. An array declared mixed that holds only numbers is byte-for-byte what number[] builds, and %HasDoubleElements confirms it
a property added after construction, o.b = 2 1.21-1.34x V8's own debug output: every object built the same way ends at the same hidden class, so a load site sees one, not two
building a string, s = s + x in a loop 0.27-0.56x faster than the push-and-join rewrite a rule would demand — V8 appends into a cons-string instead of copying
Object.keys(o).map(f) 0.94x the chain beats the fused loop, while Object.entries — one two-element array per key heavier — costs 3.59x

What it does not claim

These are microbenchmark ratios from one machine (Node v22.23.2, V8 12.4). They establish what a pattern can cost, not what it costs in your workload. turbocharge does not measure your program and never claims a speedup for it.

A truncated walk says so in words and still exits 0. The report refuses to call that run clean; the exit code is set from the finding count alone, and a CI gate reads the code, not the prose. Tracked as BUGS TC-17. The detection half of the same defect — a deep call chain that filled the 200-body cap and reported clean outright — was found and fixed on 2026-08-15.

megamorphic-elements does not check that you load anything. It reads the parameter's type and reports. A function that only reads rows.length triggers it, though nothing there can go megamorphic. Tracked as BUGS TC-8.

No rule enforces the condition in its own third column. Those conditions bound the evidence, not the code. delete-property fires on a single delete, which measured free. chained-allocation cannot see how large your array is. Tracked as BUGS TC-9.

A TypeScript union member is not a V8 map. Shape count is inferred from the declared type, so the rule can fire where no load site ever sees five maps. Tracked as BUGS TC-2.

V8 optimization state is not a speed signal. %GetOptimizationStatus reports optimized=true throughout a 5x megamorphic slowdown. Nothing here uses it.

Run it

Node >=22.18, which strips types itself, so there is no build step. TypeScript >=5.0.0 as a peer dependency — turbocharge loads your copy, so it sees the parse and the types your build sees. 

$ turbocharge src      # check annotated functions under src/
$ make test            # 46 tests, including the must-stay-silent cases
$ make example         # the before/after on three real libraries
$ make v8-check        # re-verify every V8 source citation
$ make bench           # re-run the 24-cell shape sweep
$ make bench-dispatch  # re-run the dispatch cliff
$ make bench-spread    # re-run accumulating spread
$ make bench-select    # re-run choosing between boxed values
$ make bench-chained   # re-run chained allocation
$ make bench-strings   # re-run the string refutation
$ make bench-addprop   # re-run the hidden-class refutation

The demo run takes 1.5-2.0 seconds. Almost all of that is TypeScript building a program and type-checking it, which is the price of asking real type questions rather than matching syntax. Cost scales with your program, not with how many functions you annotated. Run it as a build step, not on keystroke.

turbocharge

mark the function you need fast, and find out what is wrong with it

TL;DR
V8 speeds up your JavaScript by predicting what each line will do. While the prediction holds, that line stays on a fast path. A few ordinary-looking patterns break the prediction, and V8 moves to a slower path without saying so. Mark a TypeScript function with /** @turbocharge */ and this checker reports those patterns in it, and in every function it calls.

The idea, in one paragraph

Think of V8 as a waiter who memorises your order. Come in with the same order every day and the waiter has it ready before you sit down. Change it a little each visit and the waiter gives up memorising and asks every time. Your code does the same thing to V8. Hand one line of code five different shapes of object and it stops guessing. Delete a key from an object and V8 files that object in a slower drawer. Rebuild an array from a copy of itself inside a loop and you copy everything you already have, on every pass.

None of that looks wrong when you read it. That is the whole problem, and it is what this tool is for.

Use it

Mark the function:

/** @turbocharge */
export function total(rows: Row[]): number { … }

Point it at your source:

node /path/to/turbocharge/bin/turbocharge.ts src

It prints the line, what is wrong with it, what that cost when it was measured, and the fix. It exits 0 when everything you marked is clean, 1 when it has something to report or when it could not read your whole call tree, and 2 when the tool itself broke. A run that could not see everything is never a pass.

A real recording, not a mock-up. The function is one radash ships, vendored into examples/ unchanged. make demo rebuilds it.

What it looks for

The patternWhy V8 slows downMeasured
a fifth shape of object reaching one line V8 remembers four. The fifth makes it look up every time. 4.4–11.5x
delete o[k] the object moves to a slower kind of storage, and stays there 12.3–23.0x
acc = [...acc, v] in a loop every pass copies everything the last pass built 149–166x at 1000 items
.map(f).filter(g) the first array is built, then thrown away 6.48–7.51x
x = Lib.min(x, y) in a loop a fresh object every pass, even when nothing changed 2.56–2.87x
a call into code it cannot read V8 cannot inline what it cannot see 3.21–4.95x

Seven rules ship. Each one names the file its number came from, and you can re-run that measurement yourself.

Why the numbers are worth anything

  • Every rule had to earn its place with a measurement. A constant in V8's source is a guess about cost until a benchmark prices it.
  • Every rule also records where the same benchmark found nothing, and a test fails if the rule fires there anyway. Four shapes is fine. Two shapes is fine. Only the fifth is reported.
  • Measurements have stopped rules from shipping seven times, and taken something away from two rules that had already shipped. One rule was withdrawn completely. Those results are published next to the wins.
  • Every number on this page is read out of the raw timing data, not typed by hand. If a number and its data disagree, the test suite fails.

What it will not tell you

Whether your program is slow. It reports patterns that cost time when they are measured in a loop, on one machine, with one version of Node. If the line it flags runs twice, none of it matters. Profile first, then bring this to the function the profiler pointed at.

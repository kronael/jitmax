jitmax

A static checker for speed-sensitive TypeScript on V8 — numba's @njit, for V8: mark a hot function, and jitmax reports the patterns that push V8 off its fast path

TL;DR
Mark a hot TypeScript function with /** @jitmax */. jitmax checks it and every function it calls whose source it can read, and reports the patterns that measurably push V8 off its fast path: a fifth object shape at one property read or method call, a delete, an array built per pipeline stage. You get one error per pattern, with its file and line, the next step and the benchmark behind the rule, and an exit code a CI gate can read. Run it from your project root: bunx github:kronael/jitmax src

The middle is a real recording: the checker running against a function radash ships, vendored unchanged into examples/.

Aim

V8 is the JavaScript engine in Node, Chrome and Deno. It makes a hot function fast by compiling each property read for the object shapes it has seen there. Each read keeps up to four shapes; send a fifth through it and V8 falls back to a slow generic lookup. Deleting a property an object has can move it to slower storage. The code still returns the same values, only slower, and nothing warns you.

  • For: anyone with a TypeScript function on V8 whose speed matters.
  • Promise: every rule that claims a slowdown carries a benchmark run in the repository, with its raw timings, and cites the V8 source line where one shows the mechanism. A rule stays silent on the specific cases its own benchmark refuted that it can recognise in source, and a test fails if it fires there; it cannot see input sizes. Code the walk could not check is reported, never passed as clean.
  • Not a profiler, not a cost estimate: jitmax reads source and never runs your program. A finding is a measured candidate, not a cost in your workload; profile and benchmark your caller before you keep a change. Bun runs the checker, but every rule is about V8, not Bun's JavaScriptCore.

Use it

You need Bun and TypeScript 5.x in the project you check. jitmax parses with your project's own compiler, and bun add typescript installs 7.x, which lacks the 5.x compiler API, so pin 5.x with bun add --dev typescript@^5.9. Install the project's other dependencies too: an import that does not resolve reads as any, and the run reports it as a coverage gap.

Save this as shapes.ts in the project root. The array's elements have five shapes: 

type Row =
  | { kind: 'a'; x: number }
  | { kind: 'b'; x: number; y: number }
  | { kind: 'c'; x: number; z: number }
  | { kind: 'd'; x: number; w: number }
  | { kind: 'e'; x: number; v: number };

/** @jitmax */
export function total(rows: Row[]): number {
  let sum = 0;
  for (const row of rows) sum += row.x;
  return sum;
}
bunx github:kronael/jitmax shapes.ts

The first line is the annotated function the walk started from; the finding can sit in any function it calls. next: is what to try, and note: what that change can break besides speed. A finding prints no cost: a measured ratio depends on how much data passes through the code, and the annotation does not say.

Now mark your own hot function and run bunx github:kronael/jitmax src. Compiler options come from the tsconfig.json found from the working directory upward; paths only choose files. --help lists every argument. The README shows how a jitmax.toml switches rules off, and how a CPU profile selects functions instead of annotations.

Exit codes

0: at least one function was checked, with no errors and no coverage gaps; a warn for code that runs once, in a static field initializer, can still print. Switching off closed-world or interface-dispatch leaves the calls they report unchecked, and the run can still exit 0. 1: an error, a coverage gap such as a truncated walk or an unresolved module, or no function selected. 2: the tool failed, on invalid arguments, configuration or source syntax, or an unsupported TypeScript.

What it looks for

Eight rules ship. The first six report a pattern a benchmark measured as slower; the last two report calls the walk could not check. Each ratio is before time divided by after time: above 1 the rewrite was faster, below 1 it was slower. The ranges apply to the measured inputs, engine and hardware, not to your function.

The patternWhy V8 slows downMeasured, and what the number does not cover
a fifth shape of object reaching one property read V8 caches four shapes per read. A fifth makes it look up every time. 3.4–11.3x on reads, highest in L1 and lowest at RAM size, where memory bandwidth dominates. Two to four shapes cost 0.95–1.47x. The rule counts the property sets it can see, not runtime V8 maps.
a method called on five classes the call site sees five shapes, and V8 stops caching the lookup 12.9–22.7x, the sharpest step measured here; four shapes cost 1.52–1.65x. An object carrying its own function costs 3.5–15.8x from the second shape, which the rule misses.
delete o.k deleting a key the object has can move it to slower dictionary storage 12.3–13.6x per property read. A finding does not prove that the move happened in your workload.
x = Lib.min(x, y) in a loop the callee returns a fresh object on some path; the rule does not prove that every call allocates 2.60–2.89x. A survey of 2953 annotated functions found no site, so the rewrite is conditional advice, not a demonstrated win.
.map(f).filter(g) and other two-stage array chains the first array is built, then thrown away 1.44–1.52x for map-then-filter with construction counted. Of the other pairs, only Object.entries(o).map() was measured.
acc = [...acc, v] in a loop none: every pass copies everything the last pass built, on any engine 149–166x at 1000 items and 1766–1889x at 10000.
a call into code it cannot read the checker cannot see the callee, so it cannot tell whether V8 inlines it No speed claim: it reports code the walk could not check. One helper padded past V8's inlining budget measured 4.64–4.95x; that is one example, not a bound. Calls into Node and V8 builtins are counted, never listed.
a call that more than one body can answer several implementations or function bodies may run, or the receiver comes from outside the program No speed claim: it reports code the walk could not check. Five or more implementations reaching the call are reported as the method-call rule above.

On four real library functions, two printed fixes made the whole call slower at some size. Across 22 open-source codebases, the widest megamorphic site is in TypeScript 5.9.3's checker.ts:44260: a union of 20 distinct property sets at one property read. The examples guide has every number and count.

What it will not tell you

Whether your program is slow. It reports patterns that cost time when they are measured in a loop, on one machine, with one version of Node. A rule sees the shape of the code, never how much data passes through it or how often it runs. Profile representative inputs before you change code.

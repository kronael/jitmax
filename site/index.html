turbocharge

mark the function you need fast, and find out what is wrong with it

TL;DR
Mark one function. turbocharge checks it and everything it calls for the patterns that give up V8's fast path, and hands you the file, the line, the measured cost and the fix. Five of the six rules carry the benchmark that earned them, and the case where that same benchmark says the rule must shut up. The sixth reports what could not be checked at all.
Biome, oxlint and ESLint catch some of this one file at a time. None of them follow the call tree into the helpers and dependencies your function actually runs, and none of them ship the benchmark behind the rule.

What it is for

You have a function that has to be fast. Before it ships you want to know whether anything in it — or in anything it calls — gives up V8's fast path. That is the whole job.

Mark the function. Six rules run over it and over every callee TypeScript resolves to real source. A package shipping a .d.ts binds the call to the declaration, so most typed dependencies are the edge rather than the interior — and every call it cannot follow is listed by name, so the unchecked part of your call tree is on the report instead of assumed away.

What it gives you

  • A finding with a file and line — in the callee where the cost actually is, not the function you annotated.
  • The measured cost of that pattern, with its interval and the sweep it came from.
  • The condition under which the same measurement says the rule must stay quiet. A rule that fires there fails the build.
  • An exit code you can gate CI on, and a loud WALK TRUNCATED when coverage was incomplete, so silence always means checked.
/** @turbocharge */
export function total(rows: Row[]): number { … }

Then point it at your sources, and it reports only what it can justify:

$ turbocharge demo
turbocharge — 14 annotated functions, 8 findings

  demo/lib.ts:71  viaCallee()
    delete-property
      demo/lib.ts:66
      delete o[k] puts its object in dictionary mode
      measured 28-67x per property load once the object is in dictionary
      mode [options.md round 3b]
      fix: assign undefined, or build the object without the property

Note the second line. viaCallee carries the annotation; dropInner at line 66 is where the cost is, and nobody annotated it. You mark the function you care about, and the report points at whatever it drags in.

Exit codes are the contract: 0 clean, 1 findings, 2 the tool itself failed. A path that does not exist is a 2, never a clean run — silence on a typo is the one failure mode a CI gate cannot have.

Six rules ship: megamorphic-elements, accumulating-spread, chained-allocation, boxed-elements, delete-property, and closed-world. The first five run over every function in the tree. The sixth is the edge report: the calls that reach code we have no body for, so you know exactly how much of the run was actually checked.

The measurement

An array of objects, kernel s += r.x + r.y. Every observation is a fresh OS process, because an in-process A/B shares inline caches and that contamination invalidated an earlier round of this same work. 20 paired runs per cell, AB/BA order randomized, 95 % bootstrap interval, checksums compared inside every pair. Raw per-pair timings ship next to every aggregate, so you can recompute the interval yourself.

Ratios are one 95 % bootstrap interval each, from a single sweep run under the corrected calibration described below. Two earlier sweeps, measured before that fix, are kept on disk and are not merged into this table — mixing two methods inside one range is how you get a number nobody can reproduce.

The fifth shape is a step, not a slope. Below it the cost is real but small — 1.2x to 2.0x, and it does not even rise monotonically. At five it jumps to 10.6x in L1. That gap is the rule: four maps fit V8's inline cache and cost you a few extra map checks; the fifth does not fit, and the load becomes a hash lookup.

This corrects something we published earlier. The previous harness could not resolve anything under 1.7x and we said so — the rule stayed quiet below five because the effect was unmeasurable. With the calibration fixed it is measurable, and it is about 2x. The rule still fires only at five, but now for a better reason: not that the cost below is unknown, but that it is an order of magnitude smaller.

Independent confirmation

V8's own source sets the same boundary. DEFAULT_MAX_POLYMORPHIC_MAP_COUNT 4 lives at src/flags/flag-definitions.h:3320 and is enforced at src/ic/ic.cc:802, where the cache refuses to extend past four valid maps. The benchmark and the constant are the same fact found from opposite ends. It is the only rule here with both, and it is the reason this one is trusted more than the others.

The bigger one is not a constant factor

The cliff above is the rule with the best evidence. It is not the largest effect. Rebuilding an array from a spread of itself — acc = [...acc, v] inside a loop, or the same shape hidden in a reduce callback — copies everything the array already holds, so the work is quadratic and the ratio grows with the input:

nbuilding the arrayreading it afterwards
1,000177x (CI 157-202)0.96x (0.91-1.00)
10,0002348x (CI 1837-2892)0.98x — interval includes 1

The second column is the honest half: reading the finished array costs nothing, so the entire cost is construction, and the rule fires only where a loop re-runs the copy. A spread nothing re-runs is O(n), and stays silent.

Re-measured after a harness fix, 2026-08-11. The first version of this table came from a driver that sized each timed region from a single cold probe. That starves the slower variant of reps and inflates the ratio in the direction that ships a rule — the worst possible bias for a project whose product is the evidence. The driver now iterates the probe until it agrees with itself to within 20 %, and throws when a cell's timed region misses the 120 ms target by more than 2x, so a mis-sized cell can never be published as a result.

Re-run under the fix, the construction effect got larger — 86x became 177x at n=1,000 — and one earlier claim died outright: the spread-built array does not read meaningfully faster; both read cells now sit at 0.96-0.98x. Every superseded figure is kept on disk (spread-precal.jsonl, spread-oldcal.jsonl) rather than deleted, so the corrections are auditable.

An earlier in-process probe of ours put this same effect at 146-366x. The fresh-process harness says 2348x. Both stand as measured, by different methods.

The one the fixed harness rescued

rows.map(f).filter(g) allocates a whole array between the two stages, and the next stage reads it once and drops it. That costs 7.13x at n=1,000 with construction counted (CI 6.64-7.64). It was refused once at a measured 19.73x, before the calibration fix above — the rule only shipped when the number came down.

It also has the most interesting silent case in the set. At n=100,000 the same comparison falls to 1.45x — resolved, but far too small to justify a rule — because at that size memory bandwidth dominates and the extra allocation stops mattering. So the rule is honest about being a small-and-medium-array effect, and the tool prints that with every finding.

What it does not claim

The walk is bounded, not exhaustive. Recursion stops at a visited set for cycles and a hard cap of 200 function bodies per annotation. A call graph wider than that gets checked in part — and the tool says so, loudly: it prints WALK TRUNCATED against that function and refuses to call the run clean.

These are ratios from a microbenchmark on one machine (Node v22.23.2, V8 12.4). They say the pattern can cost that much, not that it does cost that much in your workload. Directional, not a prediction.

The cliff is read-side. Count object construction in the same loop and 3.6-10.6x drops to 1.1-3.5x, because allocation swamps reading.

megamorphic-elements fires without checking that you load anything. It reads the parameter's type and reports, but it never verifies that the function reads a property from an element — and the cost it quotes was measured on a kernel that does exactly that in a loop. A function that only reads rows.length triggers it today. Our own demo fixture is that false positive. Found by the adversarial teardown of this project, tracked as BUGS TC-8, and not yet fixed because changing what the rule triggers on is a redesign.

A TypeScript union member is not a V8 map. megamorphic-elements infers shape count from the declared element type. Five members built by one factory can share fewer maps; one declared type built two ways can be two maps. So the finding states the mechanism and leaves the judgement to you. It can fire where no load site ever sees five maps. Observing real maps at runtime is designed, not built.

boxed-elements is the weakest rule. Its 1.45-1.89x comes from one unreplicated sweep, inside exactly the band the second sweep showed this harness cannot resolve. The tool prints that caveat with the finding.

Never trust optimization state as a speed signal. %GetOptimizationStatus reported optimized=true throughout a 5x megamorphic slowdown. An earlier version of this project was a CI gate on exactly that signal. It was deleted.

Run it

TypeScript >=5.0.0 as a peer dependency, and Node >=22.18, which strips types on its own — so there is nothing to build and nothing to install beyond the TypeScript you already have. turbocharge loads your copy of TypeScript, so it sees the same parse and the same types your build sees. 

$ turbocharge src      # check annotated functions under src/
$ make test            # 16 tests, including must-stay-silent cases
$ make lint            # tsc --noEmit
$ make bench           # re-run the sweep that produced the table above

It is not fast, and the reason is worth knowing before you adopt it. The five-file demo takes 1.7-2.0 seconds wall clock on this machine, measured over three runs. Almost none of that is our analysis — the rest is TypeScript building a program and running its checker, which is the price of asking real type questions instead of pattern-matching source. It scales with your program, not with how many functions you annotated. Treat it as a build step you run on a package, not a linter you run on keystroke.

A rule that fires where the measurement rejected an effect fails make test. That test is the point of the project: the evidence can veto the code. It has, three times — the threshold shipped at three shapes quoting a five-shape number, and measuring three and four killed it; re-running the whole sweep killed the replacement numbers too; and chained-allocation was refused outright until a fixed harness brought its number down to something real.
